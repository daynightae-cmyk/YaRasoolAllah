# Quran enrichment
**Retain local Tanzil Arabic as canonical.** Quran Foundation v4 supports chapters, verses, translations, tafsirs, search, page/juz/hizb/rub, recitations. Current Content APIs require OAuth2 `client_credentials` scope `content`, backend `QF_CLIENT_ID`/`QF_CLIENT_SECRET`; token POST `https://prelive-oauth2.quran.foundation/oauth2/token`, GET `https://apis-prelive.quran.foundation/content/api/v4/chapters` with `x-client-id`, `x-auth-token`. Prelive has only surahs 1 and 2; production requires approval and paired production hosts. Cache token before expiry (documented 3600 seconds); on 401 refresh once, 403 halt, 429 bounded exponential retry. **Never put secrets in Vite/browser.**

Verse example: `GET /content/api/v4/verses/by_chapter/2?translations=<resource-id>&tafsirs=<resource-id>&words=true&page=1&per_page=50`; `verse_key` uses `2:255`. Fetch IDs from `/content/api/v4/resources/translations` and `/content/api/v4/resources/tafsirs` rather than assuming editions. Verse responses can include `id,verse_key,chapter_id,verse_number,page_number,juz_number,hizb_number,rub_el_hizb_number,words,translations,tafsirs,audio`. The by-chapter endpoint caps page size at 50. Normalize ID as `surah:ayah` and record the provider's resource ID, language, edition and attribution; compare 114/6236 with canonical corpus without replacing text.

No verified provider in this pass for precise waqf signs, i'rab or asbab al-nuzul at verse granularity. Keep these as source candidates. Revelation order and Makki/Madani claims require a named methodology; do not merge conflicting enumerations silently.
