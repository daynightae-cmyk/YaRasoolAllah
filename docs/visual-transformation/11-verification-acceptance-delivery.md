## 1. مستويات الإثبات

لا يجوز دمج مستويات الإثبات في كلمة واحدة مثل «تمام».

| المستوى | ماذا يثبت | ماذا لا يثبت |
|---|---|---|
| Static review | البنية والعقود والملفات المقروءة | التشغيل أو الشكل النهائي |
| TypeScript | سلامة الأنواع ضمن إعداد المشروع | صحة البيانات أو UX |
| Build | نجاح مسار البناء | أن الصفحات تعمل بعد التشغيل |
| Runtime | أن Route أو فعلًا يعمل في بيئة تشغيل | جودة البصريات أو اكتمال البيانات |
| Visual QA | التكوين، المسافات، الثيم، الاتجاه، الاستجابة | صحة المحتوى العلمي |
| Accessibility QA | Focus/Keyboard/Semantics/Motion | صحة البيانات أو الأداء الكامل |
| Editorial/Data QA | مطابقة الادعاء بالمصدر وحالة المادة | أن التطبيق يبني أو ينشر |
| Performance QA | أثر التغيير على التحميل والتفاعل | الدقة الدينية |
| Git delivery | أين وصلت التغييرات وعلى أي SHA | Deployment للإنتاج |
| Deployment evidence | أن نسخة معينة نُشرت في بيئة معلومة | أن كل Gate منتج نجح |

كل مستوى يسجل نتيجته منفصلًا.

## 2. الحالة المسموح بها في التقرير

| الحالة | المعنى |
|---|---|
| IMPLEMENTED AND VERIFIED | الكود موجود وكل بوابات النطاق المنطبقة اجتازت على SHA معلوم |
| IMPLEMENTED BUT NOT VERIFIED | الكود موجود لكن تحقق واحد أو أكثر لم يكتمل |
| PARTIAL | جزء من العقد فقط منفذ |
| VISUAL ONLY | الشكل موجود بينما الوظيفة أو البيانات غير موجودة أو غير مثبتة |
| NOT IMPLEMENTED | المتطلب غير منفذ |
| BLOCKED | التنفيذ أو التحقق متوقف بسبب مانع موثق |

يمنع استخدام COMPLETE أو Production Ready كمرادف لـ«Build نجح».

## 3. تثبيت خط الأساس قبل التنفيذ

قبل أي شريحة تنفيذية يجب تسجيل:

- الفرع المرجعي الحقيقي.
- SHA المحلي.
- SHA origin/main.
- Git status.
- الفروع أو PRs المفتوحة ذات الصلة.
- آخر CI يتعلق بالـSHA المطلوب إن كان هناك CI.
- الملفات التي ستُعدل.
- بوابات القبول الخاصة بالشريحة.

إذا كان HEAD مختلفًا عن origin/main، لا يبدأ المنفذ من نسخة قديمة بصمت. وإذا كان هناك عمل متوازٍ، لا يدمجه عشوائيًا.

## 4. Matrix العرض

الأبعاد الأساسية:

| البعد | القيم |
|---|---|
| Theme | Light / Dark |
| Language | Arabic / English / French / Urdu بحسب الدعم الحقيقي |
| Direction | RTL / LTR / mixed-content |
| Viewport | Mobile ضيق / Tablet / Desktop |
| Input | Mouse / Keyboard / Touch |
| Motion | Normal / Reduced Motion |
| Data state | Loading / Ready / Empty / Error / Unavailable / Unreviewed |
| Network | Online / failure حيث تعتمد الميزة على الشبكة |
| Permission | Granted / denied / unsupported حيث ينطبق |

لا يجب اختبار كل حاصل ضرب رياضي لكل فعل بلا معنى، لكن تقرير التغطية يوضح الحالات التي فُحصت بدل ادعاء Matrix كاملة بلا دليل.

## 5. أحجام الاختبار

نقاط بداية، وليست Breakpoints مفروضة:

- Mobile ضيق: قرابة 360px.
- Tablet: قرابة 768px.
- Desktop: قرابة 1440px.
- Zoom: 200% للنصوص ومسارات القراءة المهمة.

إذا كان المنتج يدعم عرضًا أضيق أو أكبر بصورة مهمة، تضاف حالة مناسبة.

## 14. بوابات الأداء

- Hero assets.
- Fonts.
- Shelves.
- Quran rendering.
- Map/SVG.
- Drawers.
- Search.

موانع القبول:

## 15. TypeScript وBuild

يسجل المنفذ الأمر **الحقيقي** الموجود في package.json الحالي.

النتيجة يجب أن تتضمن:

- الأمر.
- SHA.
- Exit code.
- الأخطاء إن وجدت.
- هل الفشل سابق للتغيير أم سببه التغيير، إذا كان ذلك مثبتًا.

لا تستخدم أسماء Scripts متخيلة ثم تعلن أنها غير موجودة كأنها فشل للمشروع.

## 16. Runtime

Runtime evidence يتضمن:

- URL أو طريقة التشغيل.
- Routes التي فُتحت.
- الأفعال التي جُربت.
- Console errors المهمة.
- Network failures المهمة.
- حالات permissions.
- Media behavior.
- Reload/Deep link behavior.

قراءة JSX لا تُسجل Runtime.

## 17. Visual QA

لكل Screenshot صالح للإثبات يسجل:

- SHA.
- Route.
- Viewport.
- Theme.
- Language.
- Direction.
- State.
- وقت أو Build إن كان مهمًا.

لا تكفي صورة الصفحة الرئيسية لإثبات التطبيق كله.

المراجعة تشرح **ما الذي فُحص**: التركيز البصري، الفراغ، الخط، التباين، قص العناصر، علاقة الأسطح، ووظيفة التكوين.

## 18. Data QA

عينات مطلوبة على الأقل:

- كتاب ببيانات كاملة.
- كتاب بلا نسخة.
- آية متاحة.
- آية غير متاحة في Dataset إن كان ذلك ممكنًا.
- حديث بدرجة ومصدر حكم.
- حديث بحقول ناقصة.
- حدث سيرة بتاريخ تقريبي.
- موضع أطلس schematic.
- مادة أطفال مع مصدر.
- ذكر بعدد وفضل منقول.
- مصدر بلا status.
- Search query خارج Index.

كل عينة تربط النتيجة بالبيانات الفعلية.

## 19. Git Delivery

يسجل:

- Baseline SHA.
- Branch إن استُخدم.
- Commits.
- Push.
- PR إن كان المسار يستخدم PR.
- Checks على SHA الصحيح.
- Merge SHA.
- HEAD وorigin/main بعد الدمج.
- حالة Worktree.

Commit ليس Push. Push ليس Merge. Merge ليس Deployment.

إذا كانت المهمة تسمح Direct-to-main للوثائق فقط، يسجل ذلك بوضوح ولا يطبقه تلقائيًا على تغييرات التطبيق المستقبلية.

## 20. قالب التقرير النهائي

| الحقل | المطلوب |
|---|---|
| Baseline | branch + SHA |
| Delivered state | branch/main + SHA |
| Files changed | الملفات الفعلية وسببها |
| Architecture | ما تغير في Shell/Providers/Tokens |
| Visual | ما تغير في كل جناح |
| Functional | الأفعال التي أصبحت حقيقية أو صُححت |
| Data/editorial | الادعاءات/الحالات التي صُححت |
| TypeScript | PASS/FAIL/NOT RUN + دليل |
| Build | PASS/FAIL/NOT RUN + دليل |
| Runtime | ما جُرب فعلًا |
| Visual QA | الحالات والصور |
| Accessibility | الأدوات والحالات |
| Performance | القياسات المهمة |
| Git | push/PR/CI/merge/sha |
| Remaining | عناصر محددة بحالات التنفيذ |
| Conclusion | أعلى مستوى تسمح به الأدلة |

## 21. بوابة الإغلاق

لا يسمح بـ«تم بالكامل» إلا إذا:

1. لا توجد Gate مطلوبة في حالة غير معلومة.
2. أي Gate فاشلة موثقة وتمنع الوصف المناسب.
3. جميع الأجنحة المتأثرة فُحصت، لا الصفحة الرئيسية فقط.
4. البيانات الحساسة راجعت.
5. Runtime وVisual QA موجودان عند الادعاء بجاهزية واجهة.
6. Git delivery يطابق SHA التقرير.
7. لا يوجد شغل مكتمل متروك محليًا بينما التقرير يزعم أنه في main.
8. لا يوجد Build أو CI من SHA قديم يُنسب إلى SHA جديد.
9. لا تُستخدم كلمة Production Ready إذا لم يُختبر النشر الحقيقي ضمن النطاق.

**هذه الوثيقة لا تمنح PASS لأي بند الآن. وظيفتها منع أن تتحول كتابة الكود أو جمال Screenshot إلى إعلان نصر قبل وجود الدليل.**
